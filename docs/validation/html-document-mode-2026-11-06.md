# HTML ドキュメントモードの検証記録

2026-11-06。PDFの読書経路をHTMLへ広げる継続作業。既存の `feature/pdf-document-mode` ブランチで実施した。originは未設定。現在地の指定は引き続きポインター直下の文とする。

## 実装と確認済みの範囲

| 対象 | 結果 |
| --- | --- |
| HTMLファイル | `.html`・`.htm`・`.xhtml`をアプリ、CLI、Finderからの文書入力として扱う。PDFと共通の全文翻訳・文書別保存・用語集・訳文パネルを利用する。 |
| URL入力 | アプリの「URLを開く…」からHTMLを取得する。Cookie・認証情報を共有しない一時HTTPセッションを使い、応答コード・HTMLのMIME型・10 MB上限を検査する。JavaScriptやリンク先リソースは実行・取得しない。 |
| 読み順 | HTML5パーサーSwiftSoup 2.14.3を固定。`main`、単一の`article`、それらがなければ`body`をDOM順に読み、見出し・段落・リスト・表の行を保持する。本文内のheaderやfooterの注記も残す。 |
| 文字コード | BOM、HTTPのcharset、XML宣言、HTMLのmeta宣言を扱う。Shift_JIS、windows-1251、引用符付きcharset、Latin1/ASCII系ラベルのブラウザに合わせたWindows-1252復号を回帰テストで確認した。 |
| ブラウザ追従 | インストール済みのブラウザを選択できる。最前面アプリ・窓のタイトルを検査し、別ページの窓が前にある場合は背後の一致窓を探して追従しない。ブラウザ変更時は追従を停止する。 |
| 自動検証 | 167件成功（Core 124、Vision 9、Runtime 5、CLI 19、App 10）。HTML抽出、HTTP応答の検査、PDFディスパッチ、保存訳再利用、読み込み競合、ブラウザ窓選択、通常ウインドウと被覆の判定を含む。 |
| 描画→OCR→照合 | WebKitで実際に描画したHTMLをVisionに通し、左右の段、同名見出し2箇所、上端で文頭が切れた文が元の文へ照合できることを確認した。ブラウザの連続実機操作を置き換えるものではない。 |

## 実モデルとURLの実動作

手元の `Bento4-HTML.zip` からHTML資料とCSSをローカル評価ディレクトリへ取り出した。元アーカイブやPDFは変更していない。

| 入力 | 読み込んだ文 | 実モデルで保存した訳 |
| --- | ---: | ---: |
| Bento4 HTML資料 `index.html` | 98 | 98 |
| 生成した読書資料をローカルHTTPから取得 | 11 | 11 |
| 公開HTTPSの [Example Domain](https://example.com/) | 2 | 2 |

PLaMo 3 Translate 2B Q4_K_Mをアプリから起動して翻訳した。ローカルHTTPのURLはアプリの入力ダイアログへ指定し、実際の200応答から11文を読み込んだ。公開HTTPSでも本文2文を読み込み、翻訳完了をアプリ表示で確認した。一時HTTPサーバーは確認後に停止した。

Bento4資料のSHA-256は `5d2fb08f456f0caa9e03e6ac2cdb18fd2e0c9427d05aef32baee3b789c2c1043`。Bento4の98文と生成資料の11文は、サーバーのないポート1を指定したCLI翻訳でも全件の保存済み訳が返った。生成資料の同名見出し2文は同じ保存キーを共有するため、11文に対して保存項目は10件である。保存項目数から翻訳済み文数を推測せず、返った全行と未訳の有無を照合した。アプリもBento4資料を98文すべて翻訳済みとして開き直した。

原文抽出、保存済み訳の読戻し、テスト・ビルドのログ、検証用HTMLと操作補助は `local/evaluations/html-document-mode-01a1aecd/` に置いた。これらはGit管理外のローカル評価資料である。通常のアプリはOCR画像・認識文字を保存しない。

## 独立レビューと修正

実装時の会話を引き継がない別agentへ要件・最終差分・一次検証ログを渡した。XML宣言と引用符付きcharsetを検出できず文字化けする指摘を受け、再現する先行テストのRed→Greenと独立CLI再確認を行った。Latin1/ASCII系のラベルも [WHATWGの対応表](https://encoding.spec.whatwg.org/encodings.json) に合わせて修正した。修正後のレビューに追加指摘はなかった。配布通知の追加と実機補助も別途レビューした。

## 通常ウインドウへの変更

検証中の「訳文が常に最前面になるのは邪魔」という指示に合わせ、訳文を通常レベルに変更した。自動表示は初回だけ背面へ出し、表示済みの窓の前後順を変えない。明示的な訳文選択では前面へ出せる。原文の前に実際に重なった窓だけが追従を止めるよう、ポインター位置での実際の窓順をキャプチャ前後に確認する。背後の訳文窓では止まらない。

通常レベルを求めるテストのRed→Greenを確認した。前後順の実機判定は、非アクティブなテストプロセスの窓一覧が安定しないため、署名済みアプリを通常起動して検証する方法へ切り替えた。実機の `normal-window-order-valid.json` はChrome前面・Chrome窓index 6・訳文窓index 10で、両窓ともlevel 0だった。その状態で以下の追従確認を実施した。

## Chromeの連続実機確認

実行前に `native-cases.json` へ正解の段落・文を15操作分記録した。正しい段落を主指標、文を補助指標とし、誤移動と特定不能は失敗に数えた。Bento4は10操作、生成資料は5操作で、異なる段落は合計10箇所である。

| 対象 | 操作 | 段落・文の一致 |
| --- | --- | --- |
| Bento4 HTML | 同じ表示内の移動、前進・逆スクロール、離れた箇所への移動、元の位置への復帰、訳文の手動スクロールからの復帰、見出し | 10 / 10 |
| 生成資料 | 同じ高さの左右の段、2つのResults、200%表示で文頭の行の上側が切れた文 | 5 / 5 |

15操作すべて正解段落・文に一致し、誤移動0・特定不能0だった。Results2箇所は原文フッターだけでは区別できないため、訳文画像で森林調査の直前の見出しと沿岸調査の直前の見出しが別々に強調されることを確認した。これは2つの静的資料による限定的な受け入れ確認であり、一般のWebサイトでの正答率を示さない。

各操作の入力後3秒間は、0.1秒ごとに前面アプリを記録した。全15操作465観測はChromeで、保持中の再活性化・再前面化は行っていない。対象窓ID・枠・タイトル・ポインター位置の被覆を保持中にも確認した。0.1秒より短いフォーカス変化は判定できない。初期選択では、対象窓だけのAXRaiseと通常のアプリ活性化を行い、必要な場合に撮影済み資料のリンクではない本文位置を一度クリックした。

手動操作は、Chromeの外に見えている通常レベルの訳文窓の部分で行った。Chrome前面の31観測を保ったままスクロール値が `0.06870373884987664` → `0.22053520592142722` に変わり、同じ原文へ戻ると元の値へ復帰した。別タイトルのBento4を前面にし、生成資料を読んでいる状態では、2箇所へポインターを動かしても訳文の現在地・スクロール値は変わらなかった。

生JSON、採点用 `aggregate-native.py` と `native-results.json`、画像をローカル評価ディレクトリへ保存した。追従開始前の準備、Codex窓による被覆で中断した測定、被覆検査で入力を送らなかった準備失敗は別ファイルに残し、成功15操作の計数には含めていない。初期のAXRaiseだけでは背後の訳文を原文より前へ出せず、覆われた箇所への手動スクロールはガードが拒否した。その測定を復帰成功とは扱わず、実際に見えている部分で測り直した。

Computer Useのブラウザタブ接続が利用できなかったため、通常UIと、ユーザーが追加許可した2つのChrome検証窓だけのネイティブ補助を用いた。無関係なChromeページには操作していない。一時的に有効にしたChatGPT.appの「デバイスの制御とデータへのアクセス」は、実機確認後にオフへ戻し、設定のオフ表示を観測した。他アプリの権限は変更していない。検証用の表示倍率を100%へ戻し、Bento4の98文すべての保存訳と追従を復元した。

HTMLは静的な本文が対象である。外部CSSの表示状態・並べ替えやJavaScript生成本文、ブラウザのログイン状態は再現しない。同じタイトルの別URLは窓タイトルだけでは区別できない。HTML単位の完了時点では枠モード1・2とKikiyaku連携デモは未実装だった。後続の[枠モードの検証記録](frame-modes-2026-11-06.md)に現在の進捗を記録する。
