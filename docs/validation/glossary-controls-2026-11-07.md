# KikiyakuとPLaMoの翻訳設定の齟齬と、依頼する修正（2026-11-07）

Kikiyakuは翻訳方向を本文のタグ、用語集をsystemメッセージで送ります。PLaMoは言語と用語集を別のパラメータで読み、配布元のテンプレートは先頭のsystemメッセージを除外します。この指定形式の差により、HTTP接続は成立しても設定が生成用入力から落ちます。

現在は、Kikiyakuの要求から原文・翻訳方向・用語集を取り出し、PLaMo用の入力へ変換するHTTPアダプタを間に置いています。このアダプタ経由では、Kikiyaku本体を変えずに設定が生成用入力へ入ります。同じ講演の字幕と資料訳を併用する限定デモも成立しています。

[未送信の報告・修正依頼](../proposals/kikiyaku-plamo3-issue.md)では、PLaMoのような翻訳モデルを意図的に対象外としているかを尋ねます。意図した制限でなければ、PLaMo向けの送信形式変換を追加し、翻訳方向・用語集が生成用入力に含まれるよう修正を求めます。対象外とする意図があるなら、必要なモデルの条件をREADMEに明記するよう依頼します。サーバー設定の調べ方や、単なる機能追加への関心を尋ねる文面にはしません。投稿は未実施です。

モデルが入力に含まれた指定を採用しなかった3条件は未解消です。固有名詞の崩れを防いだ追加辞書も検証用で、アプリの保存済み辞書には未反映です。今回の修正要求は設定を生成用入力へ渡すことであり、モデルの用語採用率の保証とは分けます。本体の実装変更、追加収音、OS権限の変更は行っていません。

## 用語集が効いたと判断できるか

比較した接続は二つです。**直接接続**はKikiyakuの既存OpenAI互換接続からPLaMoへ送るもの。**アダプタ経由**は、その間に検証用の `Tools/kikiyaku_plamo.py` を挟み、原文・翻訳方向・該当する用語をモデル専用の入力書式へ渡すものです。Kikiyaku本体はどちらも同じです。

同じ英文に `subprocess = 子プロセス`、`executable = 実行プログラム` を指定すると、次の差が出ました。

| 接続 | 辞書なしの訳語 | 辞書ありの訳語 | 分かったこと |
| --- | --- | --- | --- |
| 直接接続 | サブプロセス、実行ファイル | サブプロセス、実行ファイル | 辞書を変えても反映されない |
| アダプタ経由 | サブプロセス、実行ファイル | 子プロセス、実行プログラム | この入力では辞書が訳語を変えた |

一方、通常の「標準出力」は指定なしでも出ました。この一致を効果の証拠から外し、指定を「標準出力ストリーム」「stdout」に変えて、認識済み原文1文と資料の原文2文で比較しました。

| 識別用の指定 | 直接接続で採用 | アダプタ経由で採用 |
| --- | ---: | ---: |
| standard output → 標準出力ストリーム | 0/3 | 2/3 |
| standard output → stdout | 0/3 | 1/3 |

アダプタ経由でも6条件のうち3条件は指定を採用しませんでした。同じ要求をモデルへ直接送り直しても、採用・不採用とも同じ結果だったため、この3件は補助の変換ミスではなく、今回の2Bモデル・量子化・生成条件で残る問題と切り分けました。

## 認識誤りと固有名詞は直ったのか

元の5発話を公式字幕と比べ、`and` を `an` と認識した箇所と、`Subprocess`・`$PATH`・`FilePath` の表記が失われた箇所を特定しました。正しい原文に戻す比較では、欠けていた「追加して」が訳に戻りました。元の認識結果を修正したわけではありません。

固有名詞には、元の3語の辞書が一般名詞の `subprocess` とパッケージ名を区別していない問題もありました。特定講演向けに句単位の保護指定を加え、同じ認識済み原文を再生すると、次の表記を保持できました。

| 対象 | 元の辞書での訳 | 保護指定を加えた訳 |
| --- | --- | --- |
| パッケージ名 | 子プロセスパッケージ | Subprocess パッケージ |
| 環境変数名 | 環境変数path | PATH 環境変数 |
| 型名 | ファイルパス | FilePath |
| 資料の見出し | Swift 子プロセス | Swift Subprocess |

この追加辞書でも、一般名詞が現れる発話では「子プロセス」「実行プログラム」が保たれました。資料8文全体の比較でも、一般名詞の2文を「子プロセス」にしながら見出しの名前を保持できました。

これは**追加辞書でのテキスト再生の結果**です。元の実字幕や保存済みのデモ辞書は変更しておらず、新しい音声認識・字幕表示の実機確認とも扱いません。

## 意図が分かる部分と、先方に尋ねる部分

直接接続では、代表入力の辞書を4通りに変えても生成用入力が変わらず、用語指定のブロックがありません。固定した原文の辞書なし／ありの11組でも訳文は同じです。翻訳方向についても、同じ原文で次の結果になります。

| 日→英に指定した同じ原文 | 直接接続 | アダプタ経由 |
| --- | --- | --- |
| 水曜日の会議は中止です。 | 水曜日の会議は中止です。 | Wednesday's meeting is cancelled. |
| 子プロセスを起動します。 | 子プロセスを起動します。 | Launch a subprocess. |

Kikiyakuの実装には、system指示で発話タグの意味をモデルへ伝える規約があります。PLaMoの配布元テンプレートには、既存クライアント・サーバーのprobeとの互換性のために先頭のsystemを除外する説明があります。それぞれの処理は明示されていますが、KikiyakuがPLaMoのような専用翻訳モデルを対象外とする意図は、READMEと関連PRには書かれていません。OpenAI互換APIへ接続できるという説明だけから、あらゆるモデルへの対応義務を断定することもしません。

そのため、問い合わせは対応範囲の意図と、対象内なら既存の翻訳方向・用語集設定を失わないための修正依頼にします。変換を行う場所や実装方式は、本体の対応範囲と合わせて相談する事項です。修正方式を `/completion` へ固定する必要はなく、既存のchat APIへPLaMoが読む言語・用語のパラメータを渡す方式でも、同じ生成用入力になります。

llama-serverの設定・PLaMoの仕様・アダプタの実装調査はこちらの担当です。アダプタによる回避が成立していることは、本体の修正が必須という証明ではありません。一方で、外部アダプタの管理を省く利便性だけを、今回の報告の目的にも置きません。報告する事実は設定が失われる齟齬、依頼する内容はその意図の説明と、意図しない場合の修正です。

### 指定不採用をモデル側へ切り分けた根拠

6条件すべてで、公式テンプレートへタグなし原文と `chat_template_kwargs` の言語・用語指定を渡して得た入力と、アダプタの実送信入力が全文一致しました。アダプタ経由・同一要求のモデル直送・構造化したchat接続の訳文も、条件ごとに同じでした。この一致には、成功3件と不採用3件の両方が含まれます。

アダプタ経由と直送の生成条件・出力本文は一致し、両方とも正常なEOSで終了、切り捨てなしでした。したがって、今回の3件の不採用は、入力の欠落やアダプタによる出力加工では説明できません。結果は `model-isolation-results.json` にあります。以前の「token列も一致」という記述は撤回します。保存JSONの `tokens` は空配列で、生成token列を根拠にすることはできません。

無関係な用語だけを指定した陰性対照3組では、アダプタのモデル入力・訳文の両方が辞書なしと一致しました。通常の「標準出力」は、直接接続・アダプタ経由とも指定なしで3入力すべてに現れたため、用語集の効果には数えていません。
