# 用語集の効果を切り分ける追加検証（2026-11-07）

## 結果

既存の OpenAI 互換接続では、用語集を変えてもモデルへ渡る入力が変わらないことを確認した。翻訳方向も発話タグからモデルの言語指定へ移らない。一方、正しく構造化して渡したあとの指定無視も再現した。後者は補助による変換や応答の加工ではなく、同じ入力を受け取った2Bモデルの生成で起きていた。

「標準出力が出た」という一致だけを用語集の効果には数えない。識別用の指定に変えて同じ3入力で比較すると、既存接続は0/6、構造化した経路は3/6の採用だった。モデルに届くことと、モデルが必ず指定を採用することを分ける必要がある。

固有名詞の問題は出所を特定した。元の3語だけの登録は、パッケージ名の `Subprocess` まで一般名詞の「子プロセス」にする場合があった。講演向けの句単位の保護指定を加えたテキスト再生では、`Subprocess`・`PATH`・`FilePath` を保持でき、一般名詞の「子プロセス」「実行プログラム」も残った。これは追加辞書を使った別条件であり、元の実字幕を修正した記録ではない。

追加の収音、Kikiyaku本体・SoeYaku本体の変更、OS権限の変更、外部投稿は行っていない。

## 接続方式と用語集の対照

既存接続の用語集なし／元の3語ありは、11組すべてで訳文が同一だった。代表入力では用語集なし・元の指定・識別用指定2種類の4条件について `/apply-template` の結果も全文一致し、モデル入力に glossary のブロックがなかった。

補助側で無関係な用語だけを指定した陰性対照3組は、用語集なしとモデル入力・訳文の両方が一致した。一般名詞の `subprocess` と `executable` は、同じ原文で指定なしの「サブプロセス」「実行ファイル」から、指定ありの「子プロセス」「実行プログラム」へ変わった。

`standard output` は通常の指定「標準出力」では差を識別できない。そこで、元の指定を勝手に成功扱いせず、次の別条件を固定した。

| 識別用の指定 | 既存接続 | 構造化した経路 |
| --- | ---: | ---: |
| standard output → 標準出力ストリーム | 0/3 | 2/3 |
| standard output → stdout | 0/3 | 1/3 |

3入力は、最後の認識済み発話、READMEの `ExecutionResult` の説明、同じくクロージャの説明。全出力は `client-results.json` に保存した。通常の「標準出力」は両経路とも指定なしで3/3出ており、上表には数えていない。

## 指定無視が起きる場所

上の6条件について、実際の `Backend.translate` が送る `/completion` のpromptと生成条件、モデルの生の返答、補助が返した訳を記録した。

1. タグで包まない同じ原文と、`source_lang`・`target_lang`・`glossary` を `chat_template_kwargs` で公式テンプレートへ渡した入力は、補助が実送信するPFMLと6/6で全文一致した。
2. 補助の要求をそのままモデルへ直送した出力、補助経由の出力、正しい構造化指定のchat出力は6/6で全文一致した。
3. 補助経由と直送のtoken列・生成条件も一致し、両方とも正常なEOSで終了、切り捨てなしだった。3件の指定無視が同じまま再現した。

したがって、この3件は用語の除外や応答の加工が原因ではない。結果は `model-isolation-results.json`。既存の接続で情報が入力から消える問題と、届いた指定をモデルが採用しない問題を、一つの「用語集が効かない」にまとめない。

## 元の字幕の認識と、固有名詞の保護

元の5発話と公式字幕を全文照合し、次を特定した。`you’ll` と `you'll` の違いは表記差として別に記録した。

| 公式字幕 | 認識済み原文 | 切り分け |
| --- | --- | --- |
| adding **and** importing | adding **an** importing | 語の認識違い。正しい原文に戻すと訳に「追加して」が戻った。 |
| Subprocess package | subprocess package | パッケージ名の大文字を失った。一般名詞用の登録もこの語に適用された。 |
| $PATH | path | 識別子の表記を失った。 |
| FilePath | file path | 型名が一般の語に分かれた。 |

保護指定には `Swift Subprocess = Swift Subprocess`、`Subprocess package = Subprocess パッケージ`、`FilePath = FilePath`、`file path = FilePath`、`path environment variable = PATH 環境変数` を加えた。特定講演向けの辞書であり、一般の会話すべてへ適用する設定にはしていない。

履歴ありの再生では、元の3語を使った5訳が元の実字幕と5/5で全文一致した。同じ入力・順序で辞書を変えた保護指定の群では、パッケージ名・PATH・FilePathを保持し、一般名詞が現れる3発話では「子プロセス」、2発話では「実行プログラム」を維持した。既存接続の辞書なし／元の3語ありは、この再生でも5/5で同一訳だった。各群はその群の訳を履歴へ入れるため、これは発話列全体への設定の効果であり、履歴の訳文まで固定した1文ごとの比較ではない。個別入力への直接効果は履歴なしの試験で確認した。

資料8文全体でも、空辞書では一般名詞の2文が「サブプロセス」、元の3語と保護指定では「子プロセス」になった。見出しは空辞書で `Swift Subprocess`、元の3語で「Swift 子プロセス」、保護指定で `Swift Subprocess` だった。元の3語だけの登録が見出しの名前を崩すことを、同じ資料で確認した。

## 無効な対照と訂正

最初の `document-none.*` の8出力は、CLIで `--glossary` を省略すると文書の保存辞書を自動読込するため、辞書なし対照として無効だった。そのファイルを保持して集計から除外し、0バイトの辞書を明示した `document-none-explicit-empty.*` の8文だけを再実行した。明示した辞書がある場合は自動辞書を併用しないことを `Sources/SoeYakuCLIKit/Commands.swift:27-30` でも確認した。
