# 追加検証で分かったことと、外部相談の位置づけ（2026-11-07）

変換補助を使えば、Kikiyaku本体を変えずに翻訳方向と用語集をPLaMoへ渡せることを、同じ原文で確認できました。同じ講演の字幕と資料訳を併用する限定デモは成立しています。

この結果だけで、Kikiyaku本体への対応が必要だとは言えません。サーバーやモデル側の設定方法は、こちらで調べる事項です。外部相談を当然の次工程とする前提を取り下げ、[未送信の提案](../proposals/kikiyaku-plamo3-issue.md)は、変換補助の管理を省くために本体への機能追加を望む場合の案として保管します。投稿は保留中です。

モデルが届いた指定を採用しなかった3条件は未解消です。固有名詞の崩れは追加辞書で防げましたが、その辞書は検証だけに使い、アプリの保存済み辞書には反映していません。今回行ったのは検証と文書の修正です。本体の実装変更、追加の収音、OS権限の変更、外部投稿は行っていません。

## 用語集が効いたと判断できるか

比較した接続は二つです。**標準接続**はKikiyakuの既存OpenAI互換接続からPLaMoへ送るもの。**変換補助あり**は、その間に検証用の `Tools/kikiyaku_plamo.py` を挟み、原文・翻訳方向・該当する用語をモデル専用の入力書式へ渡すものです。Kikiyaku本体はどちらも同じです。

同じ英文に `subprocess = 子プロセス`、`executable = 実行プログラム` を指定すると、次の差が出ました。

| 接続 | 辞書なしの訳語 | 辞書ありの訳語 | 分かったこと |
| --- | --- | --- | --- |
| 標準接続 | サブプロセス、実行ファイル | サブプロセス、実行ファイル | 辞書を変えても反映されない |
| 変換補助あり | サブプロセス、実行ファイル | 子プロセス、実行プログラム | この入力では辞書が訳語を変えた |

一方、通常の「標準出力」は指定なしでも出ました。この一致を効果の証拠から外し、指定を「標準出力ストリーム」「stdout」に変えて、認識済み原文1文と資料の原文2文で比較しました。

| 識別用の指定 | 標準接続で採用 | 変換補助ありで採用 |
| --- | ---: | ---: |
| standard output → 標準出力ストリーム | 0/3 | 2/3 |
| standard output → stdout | 0/3 | 1/3 |

変換補助ありでも6条件のうち3条件は指定を採用しませんでした。同じ要求をモデルへ直接送り直しても、採用・不採用とも同じ結果だったため、この3件は補助の変換ミスではなく、今回の2Bモデル・量子化・生成条件で残る問題と切り分けました。

## 認識誤りと固有名詞は直ったのか

元の5発話を公式字幕と比べ、`and` を `an` と認識した箇所と、`Subprocess`・`$PATH`・`FilePath` の表記が失われた箇所を特定しました。正しい原文に戻す比較では、欠けていた「追加して」が訳に戻りました。元の認識結果を修正したわけではありません。

固有名詞には、元の3語の辞書が一般名詞の `subprocess` とパッケージ名を区別していない問題もありました。特定講演向けに句単位の保護指定を加え、同じ認識済み原文を再生すると、次の表記を保持できました。

| 対象 | 元の辞書での訳 | 保護指定を加えた訳 |
| --- | --- | --- |
| パッケージ名 | 子プロセスパッケージ | Subprocess パッケージ |
| 環境変数名 | 環境変数path | PATH 環境変数 |
| 型名 | ファイルパス | FilePath |
| 資料の見出し | Swift 子プロセス | Swift Subprocess |

この追加辞書でも、一般名詞が現れる発話では「子プロセス」「実行プログラム」が保たれました。資料8文全体の比較でも、一般名詞の2文を「子プロセス」にしながら見出しの名前を保持できました。

これは**追加辞書でのテキスト再生の結果**です。元の実字幕や保存済みのデモ辞書は変更しておらず、新しい音声認識・字幕表示の実機確認とも扱いません。

## 本体への機能提案と、こちらの調査をどう分けるか

標準接続では、代表入力の辞書を4通りに変えてもモデルへ渡る入力が変わらず、用語指定そのものが消えていました。固定した原文の辞書なし／ありの11組でも訳文が変わりませんでした。これは今回の接続条件で変換が必要な根拠であって、その処理をKikiyaku本体に置く必要性の証明ではありません。変換補助を使う方法では、既に本体を変更せず設定を渡せています。

翻訳方向も同じ原文で比較しました。次の2例では、変換補助ありで指定した英語になりました。

| 日→英に指定した同じ原文 | 標準接続 | 変換補助あり |
| --- | --- | --- |
| 水曜日の会議は中止です。 | 水曜日の会議は中止です。 | Wednesday's meeting is cancelled. |
| 子プロセスを起動します。 | 子プロセスを起動します。 | Launch a subprocess. |

Kikiyaku側だけが判断できるのは、PLaMo向けの送信方式を製品の対応範囲に含めるかです。本体への機能追加を提案する目的は、外部の変換補助の起動・終了管理を省くことになります。元の利用目的の達成と、この運用上の改善は分けて判断します。提案文から、サーバー設定の発見をメンテナーへ依頼する質問は削除しました。

llama-serverの標準設定については、起動時の固定JSON値を渡す `--chat-template-kwargs` と、テンプレートを差し替える `--chat-template-file` があることを確認しました。検証済みの配布元テンプレートはKikiyakuのsystemメッセージを除外するため、固定の起動設定だけでアプリのプロファイル変更を取り込む実装にはなっていません。ただし、独自テンプレートを含めたサーバー側の方法を尽くしていないので、サーバー側で解決できないという主張もしません。追加調査が必要なら、こちらが行います。
